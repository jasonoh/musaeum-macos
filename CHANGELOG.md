# Changelog

All notable changes to Musaeum. Format loosely follows [Keep a Changelog](https://keepachangelog.com); versions follow semver once the app is packaged.

## [Unreleased] — 2026-10-09

### Added

- **PDF-only books now open in Musaeum's own reader.** The app prepares a reflowed book once, showing progress while it works, and a book it cannot lay out opens in Preview with a line saying why. This is the last slice of the PDF reflow design (`docs/superpowers/specs/2026-10-07-pdf-reflow-reader-design.md`, plan `docs/superpowers/plans/2026-10-09-pdf-reflow-slice-3.md`) that the reader can reach: a PDF-only book opens as `reflow`, the app asks the sidecar for the pass and broadcasts its progress, the finished book is served over a route of its own and rendered by the engine each client already owns, and the original is one gesture away — the contents panel, find-in-book and typography all work on it exactly as they do on an EPUB. Measured in the running app on 2026-10-09: a 24-page paper was ready at **5.0 s** (frames `start` → `1 … 24 of 24 pages` → `writing`) and reopening a prepared book was **0.42 s**; an image-only book refused in **103 ms** and Preview opened the original PDF with _"no page carries a text layer"_ on the toast. The artifact is **not** a format: no book gains an EPUB, and `GET /api/books/{id}/file?format=reflow` still answers 404 until the wire's slice documents it. What the slice deliberately left: the phone's own route, and the 45 `mobi`+`pdf` papers, which the Mac still reads as a `mobi`.
- **A phone can ask the Mac for a PDF-only book as a reflowed EPUB.** The REST API reports `reflow: { available }` on every book and serves `GET /api/books/{id}/file?format=reflow`: it answers 202 with the pass's progress while the Mac prepares the book, the EPUB when it is done, and a named refusal when the book has no text to lay out. This also gives the papers that hold both a MOBI and a PDF a way to get their reflowed copy: the phone asks. Documented first in `docs/rest-api.md`; the iOS client is the next slice.

### Changed

- **Sending an EPUB-only book to a Kindle no longer needs Calibre.** The conversion to AZW3 is done by the app's own writer inside its Python sidecar, so a machine with no Calibre at all sends exactly the same way — nothing to install, nothing to point at. The `ebook-convert` field is gone from Settings, and an install that had set one keeps a harmless leftover value that nothing reads. Calibre's _library_ is still readable for a migration; only the dependency on its converter is gone.
- A send that converts and caches a copy now records it in the library's own `metadata.json` and in `catalog.json`, not only in the app's local database — so a catalog rebuild, or a second Mac adopting the same library, keeps the already-converted copy instead of forgetting it.

### Fixed

- A cached AZW3 could silently drop out of a book's format list: the send recorded the new format only in the local cache, and the next catalog adoption then pushed the older list back over it, library-wide, while the file stayed on the share. Measured on the real library (a book sent two days earlier had its AZW3 on disk while `metadata.json`, `catalog.json` and its database row all said EPUB).

### Notes

- **What else landed behind the surface, and what is not wired to it.** The reflow pipeline arrived in two slices — the Apple-Vision layout helper with a rebuilt gate (2026-10-08), then the production pass behind the `reflow_pdf` RPC: `{book}/derived/reflow.epub` beside its version stamp, page-map progress frames, a confidence gate that refuses a book rather than laying it out badly, and one lock per artifact (2026-10-08/09). The layout helper also ships in packaged builds as of that work, which is what lets the reader work outside a dev tree. Separately, an in-house EPUB → AZW3 writer landed (2026-10-06/07) and opened three converted books on a real Kindle Oasis on 2026-10-07 — cover, TOC, internal links and a kept reading position — and it is what a Kindle send runs as of 2026-10-09 — the Calibre-free conversion removed the `ebook-convert` dependency entirely, so the app calls **no Calibre binary at all**.

### Changed

- **A cover on the grid opens when you point at it, instead of the whole card lifting.** The cover rotates a few degrees about its spine — the spine does not move, the fore edge swings toward you — while a page block hinged on that edge swings into view, so the book opens under the cursor rather than rising off the shelf. ## [Unreleased] — 2026-09-28

### Added

- Books reach a shelf by being dragged onto it — slice 3 of the bookshelves design (`docs/superpowers/specs/2026-09-27-bookshelves-design.md`, plan `docs/superpowers/plans/2026-09-28-bookshelves-slice3.md`). Dragging a card or a list row carries the whole selection when the dragged book is part of one and that book alone otherwise — the drag never changes the selection — and the sidebar's shelf rows highlight under the pointer and take the drop, with the toast coming from the membership module exactly as it does for the menu route. Dropping on the row of the shelf that is **open** refuses (no ring, no toast — the refusal suppresses the browser's `drop` outright), dropping on **+** or on the empty-state *New shelf* row opens the name field and creates the shelf with the dragged books, and a drop while the share cannot take a write refuses — no ring, a `dropEffect = 'none'` cursor, and the create controls' disabled `title` carrying the storage label (offline was not exercised live). A Finder file drop over the shelf section or the create controls still reaches the window's import handler: the refusal belongs to book drags only. A drag whose source row scrolls out of the virtualized view mid-drag still delivers: the payload lives in a module-level slot (`src/lib/book-drag.ts`) because Chromium protects the drag data store (`getData()` is empty in every `dragover` — measured) and a source can unmount before the drop, with the window's `drop`/`dragend` clearing it (`useBookDrag`, mounted once). A book drag never raises the Finder import overlay, and a foreign drag is never answered from the slot. **No main-process, IPC, preload or REST change**, and no `src/types/` change: `src/` only, 8 code files and 5 test files, built against a driven-drag CDP instrument whose measurements — four spike answers, the divergences, and what was and was not exercised live — are recorded in the plan's *Built — slice 3* section.
- **The phone can browse shelves now — the shelf surface is on the wire, and `apiVersion` stays 1** — slice 5 of the bookshelves design (`docs/superpowers/specs/2026-09-27-bookshelves-design.md`, plan `docs/superpowers/plans/2026-09-28-bookshelves-slice5.md`). `GET /api/shelves` answers from the cache — 200 whatever the share is doing — each shelf with the count of books the library holds and the shelf file's own clock; `?shelf={id}` scopes both library reads through the same WHERE builder the Mac's own views use, with `sort=shelf_added` descending as the default inside a shelf and only there (a `sort=shelf_added` with no shelf to order by is a 400, as is a present-but-empty `shelf`, and an unknown shelf is a 404 on both routes); and every book payload on all four routes that carry one gains `shelves` — the ids only, always present, `[]` when none, filled from one batched read per page, so a rename changes the shelf list and no book. The API's **first `DELETE`**, `PUT`/`DELETE /api/shelves/{id}/books/{bookId}`, toggles membership with no body and answers `{ "book": … }` — the book **read back after the write** — and is idempotent on the service's own rules (an existing member keeps its `added_at`; removing a non-member succeeds), which is what makes a queued phone toggle safe. Both writes run through `services/shelves.ts` — the same funnel as every Mac-side shelf action — so a phone's toggle lands in `shelves.json` and updates the Mac's sidebar through `shelves:changed`. The order of refusals is the cover/file routes': the share first (503 `library offline`, `Retry-After: 5`, refused before anything is written), then the resources (404, pre-checked on the cache, with the writer's own *That shelf no longer exists* as the re-read race's backstop); an unreadable `shelves.json` answers 500 and is never overwritten, with the reason in the Mac's log. The three contract artifacts moved together — the document's `json payload=` blocks, the goldens and the shaper, with the parity case deciding them field for field (the new `shelves` and `membership` blocks included) — and so did the smoke script, which now lists shelves, scopes the library by one (checking the scoped total against the shelf's own count), exercises the 404s and 400s, and borrows the run's own upload for the membership pair, **restoring the shelf** it borrowed it from. **No preload, renderer, IPC or `src/types/` change** — main process, the document and the script; `apiVersion` stays **1** so an installed phone is not locked out, and the phone's capability probe is `GET /api/shelves` itself (404 → no shelf UI). 6 code files and 5 test files; `npm test` **1884** across 87 files; the live run, and what it did and did not exercise, are recorded in the plan's *Built — slice 5* section.

### Added
- **A book you send to the Kindle now arrives with its cover.** The device stopped generating these for itself — measured 2026-09-17 against the 1,567 files on this Kindle: every one of the 91 books copied since Calibre's last connect landed without a cover, each attempt leaving a 0-byte `…_portrait.jpg.tmp.partial` behind — and no Musaeum code path has ever written one, so a fresh send has landed as a blank tile since the day it was copied. A send now writes the device's own cache entry, `system/thumbnails/thumbnail_<uuid>_<cdetype>_portrait.jpg`, named from the identity **inside the file that was copied** rather than from the book: one book sent as azw3 and as mobi carries two different uuids (measured on *Red Rising*, `5f8e82e4…` and `1b3e27dc…`) and only the copy's own is the name the device looks up. It also clears the stale `…tmp.partial` beside it, which is what hides a cover that is already there — 148 books on this device were carrying one behind a marker. The jacket is **fitted** into the device's box (330×500) and never upscaled or stretched: handing the encoder both dimensions squashes a jacket that is not the box's aspect by ~13 %, so only the binding one is passed, and a 2:3 jacket lands at 330×495 with five pixels of the box unused rather than at 330×500. **Nothing here can fail a send, and nothing here reaches the screen:** a book with no jacket and a PDF send are ordinary — no entry, no log line — while a jacket that cannot be encoded or a device that refuses the write logs one warning and the send still reports done. The only file it ever deletes is the exact marker for the entry it is writing, because this is the app's **second** path that deletes files on a mounted device and the first one already deleted a real file off a real Kindle from a passing test run. 6 files (the design budgeted 4 — see below): `services/device-covers.ts` with 14 cases of its own, one hook plus 7 cases in `transfer-queue`, the `electron` mock's codec (a loud throw, since the codec is Chromium's and vitest has none), and `scripts/device-cover-probe.ts`, which decides the real codec against the *shipped* writer — on three real jackets it wrote **24,114 / 28,886 / 34,366 B** at **330×499 / 330×496 / 330×441**, every one inside the device's own 22–47 KB band, at 124–271 ms per write (the SMB read of the jacket, not the encode). `npm test` **1630** across 72 files (+21), `typecheck` / `lint` / code `prettier` clean, **mutation campaign 12 of 12 killed** with every red attributed to the case that names it. **The row that survived the first run is the one worth reading:** every case derived its expected filename from `deviceCoverName(...)`, so swapping the uuid and cdetype arguments inside it moved both sides of the assertion and nothing reddened — the name is a literal now, and that row kills five cases. The two extra files over the design's budget are both forced: the mock needs a `nativeImage` export or the module fails at link time in every test that loads it, and the real codec has no unit decider at all under Electron-as-Node. **Not yet, and deliberately:** the files already on the device keep the covers they never had *until the next connect* — the connect-time pass that fills those in is designed (`docs/superpowers/specs/2026-09-26-device-covers-design.md`, slice 2), and two readings that want the device plugged in are open with it (whether the Kindle renders a *fitted* entry, and whether the marker's spelling is what its firmware uses). _Corrected in place 2026-09-26, the same day: that pass **landed**, see the entry below — the two readings are still open and still gate nothing._
- **The books already on your Kindle get their covers back the next time you plug it in — and only once.** The send half fixed books you copy from now on, which left the 1,567 files already on the device with whatever covers they never had (77 entries had ever been written by hand, in one session at the terminal). The app now fills those in itself, one entry per distinct jacket, in a pass that runs behind the identity pass on every connect and never in front of it — behind it because the pass needs to know which book each device file *is*, and that reading is what the identity pass has just finished computing; behind it also because it must add **no time to a cold connect**, so it opens **nothing** on the device: it reads one directory listing of `system/thumbnails/`, decides from what it already knows, and reads each jacket off the share once no matter how many formats that book has on the device. **The first connect after this is the one that works**, and every connect after it is a single listing that finds nothing to do. Which jacket a file gets comes from the same rule that decides whether the book is on the device at all — not a second rule that could drift away from it — so a file the library cannot attribute to a book, and a file **two** books both claim, both get no cover rather than a guess: the wrong jacket on the wrong tile is worse than a blank one, and a book you re-send is one jacket away from right. Nothing here can fail a send or a connect, nothing reaches the screen, and the only file it ever deletes is the same stale marker the send half clears — so a marker left for a book that is no longer on the device stays exactly where it is. **Not built, and named so you know:** whether your Kindle draws an entry whose jacket is not the box's shape (a 1:1.336 jacket lands 330×441, not 330×500) is still unmeasured, because it needs the device plugged in — the entry is named by the key the device looks up either way, so the cost of that reading being wrong is one blank tile, not a file. 4 files: the pass and its counters in `services/device-covers.ts`, the device→book view plus the scheduling in `device-manager.ts`, and their two suites. `npm test` **1649** across 72 files (+19), `typecheck` / `lint` / `prettier` clean, **mutation campaign 12 of 12 killed** with every red attributed to a named case — and the one that survived the first run is the interesting one: the guard that stops the pass when there is nothing to write for was sitting *behind* an identical guard one level up, so its own test was passing without deciding anything. The case that decides it now comes from the other side.

## [Unreleased] — 2026-09-25

### Added
- **A cover the app could never find is now one you can hand it yourself — from any image on this Mac.** The picker could only ever offer jackets the fetchers returned, so a person holding the right cover in a file — a scan, a designer's export, an edition whose artwork no API carries — had no way in. Under the candidate tiles there is now **Choose an image…**, which opens a file sheet and writes what you pick through the same path a picked jacket takes: the same 600 px and 200 px renditions, the same row, the same `metadata.json`, the same catalog, and the same **hold** — so a metadata fetch leaves your image alone until you hand the cover back. Reviewed by the same rule as everything else here: a `.txt` renamed to `.jpg`, an image under 120 px on a side, a file that cannot be read, and a **truncated** JPEG each get their own sentence and **write nothing at all** — the last one found by probing the running app rather than by its tests, because the first guard read only the image's header and a damaged file failed later with a Python exception where a sentence was promised. **Both of those sentences are the sidecar's own words**, so the screen cannot invent a different reason than the one the writer had. Nothing about the choice is invisible: the panel and the grid card repaint in place, the dialog says *Your image is now the cover on this book*, and the *Held:* line is re-read rather than assumed. **Deliberately not here:** crop or rotate, and the Google-ISBN-miss fallback.
- **You can now choose which jacket a book wears, and the app can no longer make that choice invisibly.** Until today the only way a cover changed was a metadata fetch — and when a fetch picked one you did not want, there was nothing to do about it: re-fetching was *right* not to help (the file's bytes and the record already agreed), and the conflict queue only ever asks about covers it happened to queue, which a fetch that won by a hair never does. The detail panel's cover now has a **Choose cover** control under it, and the right-click menu has **Choose cover…** beside *Edit metadata…*; either one opens a dialog listing **every jacket the app actually gathered** — Google Books, OpenLibrary, and the cover inside your own file — each with its source and its pixel size, and marked so you can see the two facts that matter: **which one your book is wearing now** (*On your book now*) and **which one a fetch would write** (*A fetch would write this*). When they are different — the case this feature exists for — both marks show. Picking one writes it to the book, updates the grid card and the panel in place with no relaunch, and **holds** the cover: from then on a metadata fetch leaves it alone until you hand it back with *Hand it back to Musaeum* in the same dialog. The editor's summary no longer implies a padlock that does not exist for Cover: it says where a cover is released. **One thing this did not do at first:** it offered only the jackets the app had gathered, so a book whose *right* jacket was one the fetchers never returned stayed out of reach. Both answers have since shipped, and they are the two entries above this one: **Look for more covers** asks the questions the fetchers had not asked, and **Choose an image…** takes one straight from this Mac.
- **A jacket the app never found is a search away now — and searching changes nothing by itself.** The picker could only offer what a metadata fetch had already gathered, so a book whose *right* jacket never came back was simply unreachable: *Topology of Violence* wore a Spanish-language Herder jacket while its English MIT one sat one question away. Under the gathered candidates there is now **Look for more covers**, and it asks the questions the app had not asked — the book's **other editions**, by the identifiers OpenLibrary already lists for the work, then by **title and author** as a structured query (`intitle:` with `inauthor:`), never a free-text box, which returns 300 mostly-wrong hits on this very book. On the real book it found the correct jacket in **six seconds** — and found **two** of them, which is why the second group says exactly what it can support: its tiles are headed *FROM A WIDER SEARCH*, they carry *a fetch would not write any of them — nothing changes unless you pick one*, and no search result is ever marked as what a fetch would write, because a fetch asks the other question. Searching writes nothing, applies nothing and persists nothing; picking is the same write the dialog always did, and it holds the cover as before. **Deliberately not here:** widening what a *fetch* writes — Google outranks OpenLibrary in the scoring, so a re-fetch that asked the wider question would swap jackets library-wide, unasked, across 7,109 rows — and crop/rotate.

## [Unreleased] — 2026-09-24

### Fixed
- **A library in a folder on this Mac no longer triggers mount attempts against a server you do not have.** With the folder renamed, moved, or on a drive that is not plugged in, the app used to run `open -g smb://nas` every 5 s, then 15 s, then 60 s, forever — and the banner's only button, _Retry Now_, ran the same thing. It now knows whether your library is a **folder** or a **share** (the folder you chose decides it, and Settings reports which one it settled on), so a folder gets no retry loop at all: nothing is coming back on its own, and the fix is to tell the app where the books went. A share behaves exactly as before — the mount attempt, the backoff, the manual retry.
- **The app stops claiming it is reconnecting when it is not.** A failed attempt used to pin the status at _"Reconnecting to the library…"_, so the half of the message that matters — _editing is disabled_ — was shown once and then replaced for good. It now returns to the offline state between attempts, and a write refused while your library is a folder says the folder is missing (and that you can choose where it went) instead of asking you to reconnect to a NAS. **(Corrected the same day by the slice that followed:** every word for a missing folder now exists — composed in the main process with the rest of the storage copy — and the banner, the sidebar row and Settings gained it together; the entries below are that work.)**

### Changed
- **Every word the app shows about your library's storage now comes from one place in the background process, so the sidebar and Settings can no longer tell you two different things — and none of it assumes you have a server.** Each of the five states a library can be in had its copy written out twice, once in the sidebar's status row and once in Settings, each as its own chain of conditions; a **folder that has moved or been renamed** fell through both to the words a **dropped share** gets — *"Library offline — browsing from cache, editing disabled."*, with no retrying clause (a folder arms no timer, and that clause is the only thing that makes the sentence honest) beside a ***Retry Now*** whose only effect was a no-op. The sentence, the one-word status and **which recovery the state offers** are now composed in the main process and travel to the screen as values (`services/storage-copy.ts`, with 31 cases of its own). So: a library that is a folder on this Mac reads ***"Library folder missing — browsing from cache, editing disabled."*** and offers **Locate Library Folder…** — which opens the picker **at the folder that went missing**, or at its nearest surviving ancestor when that is gone too — where *Retry Now* used to sit; a share reads exactly as before, retrying clause and all; and the two rows render one shared word each (*Connected*, *Not configured*, *Reconnecting…*, *Offline*, *Folder missing*) instead of two independent guesses. Source-walked as a rule rather than grepped once: a new case fails the moment any file under `src/` types *"Reconnect to the NAS…"* or *"from the NAS"* by hand again.
- **Settings now says which of the two your library is, and stops asking a folder about an SMB URL.** The Library section gains a **Storage** line — *Local folder* or *Network share*, with the note that it was resolved when the folder was chosen — and an advisory line naming the cloud client when the chosen folder sits inside one. Three ways in: the *Import…* button (native picker, multi-select), a drop anywhere on the Appearance section, or the drop-box folder at `~/Library/Application Support/Musaeum/themes` with a *Reveal in Finder* and a *rescan* control beside it. **base16 (`.yaml`) and iTerm2 (`.itermcolors`) files both work**, and every row names the provider it came from — the same scheme via two providers is genuinely two palettes (gruvbox's base16 `base05` is `#d5c4a1` where its iTerm foreground is `#ebdbb2`), and the label is what makes that visible instead of confusing.
- **An imported theme keeps working after its file is gone.** What gets stored is the *derived* palette, never a reference to the file, so the values survive the source being moved, renamed or deleted — the themes folder is yours to organize and nothing is ever copied into it or normalized beside it. A row also says what its derivation had to approximate (a scheme with no surface ramp gets one inferred, and the row discloses which stops were invented) rather than silently guessing.
- **A theme that cannot be made readable is refused with its reason, in its own row**, and the app keeps the palette it already had. A malformed file, an unreadable one and a palette that cannot hold a legible contrast are each reported per file: importing five files with one bad one still imports the other four, and the folder rescan reports what it could not read instead of failing.
- **A metadata re-fetch now says what it did.** Pressing Re-fetch metadata used to return instantly and report nothing: a successful fetch announced itself by quietly redrawing the card, and a failed one said nothing at all. The button spins while the fetch runs (and the book's card carries a spinner too, so a refresh started from one book and left behind is still visible), and the answer arrives when it settles — *Metadata updated* with the fields that actually changed, *No new metadata found* when the sources had nothing new to add, or the failure's own message. The last of those is the one that mattered most: hydration failures are non-fatal by design and were only ever logged, so a timeout at Google Books was indistinguishable from a book that was already perfect.
- **Conflicts queue a review from the report** — a refresh that found disagreement offers a *Review* button on the same report rather than leaving the queue badge to be noticed.
- **A request to re-fetch is available from the context menu** for a single book, matching the detail panel's button and reporting identically.
- **A small toast surface** (`components/shared/Toasts.tsx`, owned by the UI store) for work that finishes out of the reader's sight. It carries those reports, replaces the two blocking `alert()` calls the detail panel and context menu used for failures, and now also reports the end of a bulk refresh, whose status-bar counter previously vanished without a word.
- **A card says what file it is.** The only way to learn whether a book was an EPUB or a PDF was to open it, which is the wrong trade for something glanced at across 7000 covers. Each card now carries a small format chip in the bottom-left of its cover — the primary format, plus a count of the rest (*EPUB +1*), with the full list in the chip's tooltip. PDF sorts last in that preference but is never what gets hidden: a PDF-only book reads *PDF*, which is the label most worth seeing at a glance, since a PDF is never converted and has no in-app reader.

### Changed
- **`importer.hydrate` returns what it did** — `{ok, changed, conflicts}` or `{ok: false, error}` — instead of only logging it. ### Fixed

### Added
