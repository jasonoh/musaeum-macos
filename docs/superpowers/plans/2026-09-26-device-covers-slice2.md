**Date:** 2026-09-26
**Slice:** 2 of 2 (the connect pass — fills in the entries for the files already on the device)
**Annex to:** `docs/superpowers/specs/2026-09-26-device-covers-design.md` (D1–D7, AC1–AC17, and its _Built — slice 1_ section)
**Read first:** `docs/invariants/device-transfer.md` (the cover rule, and the harness hazards section — a fixture named after a real file deleted a real file off an attached Kindle once), `electron/main/services/device-manager.ts:143-254` (the scan → header pass → broadcast chain this pass hangs off), `electron/main/services/device-covers.ts` (slice 1's writer, whose naming and marker rules this slice reuses unchanged).

## What this slice is

1. The header pass's tail schedules a **cover pass** for the same device, coalesced per device exactly as the header pass coalesces itself, and skipped outright for a device whose file set is empty.
2. The cover pass asks `device-manager` **which book each device file carries** — a view of the same match rule presence uses, not a second implementation of it — and asks `device-covers` to write the entry the device will look up for each file that needs one.
3. It writes only where an entry is missing, reads a book's jacket **once** however many files that book has on the device, and reads nothing off the device at all: one `readdir` of `system/thumbnails/`, no stats, no opens.
4. It is non-fatal and invisible: a log line with its counts is the whole surface. No event, no `TransferJob` field, no persisted record, no renderer file.

Nothing in the parent spec's D1–D7 is re-opened. The readings below are the ones the spec left to the build.

## Readings this slice had to settle

Each with the alternative it beat and the condition that would revive it. These are the slice's own D-series.

- **R1 — the pass's seam is `fillDeviceCovers({ mountPath, owners, coverPathFor })`, and `device-covers.ts` holds no matching logic.** The owners are the device-manager's answer (D7's view); the jacket lookup is injected, so the module stays pure over an injected path the way slice 1's writer is. _Beat:_ the pass reaching into `deviceContents`/the identity cache/`db` itself, which would put module state and two `db` reads inside the encoder module. _Revived:_ a second consumer of the pass that has no `device-manager` to ask.
- **R2 — the file→book direction is the forward rule _factored_, not re-implemented.** `pathsCarryingBook(deviceId, book, stems, device)` is extracted from `getOnDeviceBookIds`'s own condition (the stem rule, `filesCarryingBook`, the send receipt) and both functions call it, so AC13 holds by construction rather than by agreement. `holdsFileWeSent` disappears as a standalone predicate and becomes the receipt arm of that function. _Beat:_ walking the identity cache and inverting each arm — that is the second implementation of the match rule D7 exists to forbid. _Revived:_ never; the factoring is the point.
- **R3 — one writer, two sources for the name. `writeEntry(dir, name, bytes)` is extracted, and slice 1's `writeDeviceCover` becomes _read the identity off the file_ → encode → write.** The pass must **not** call `writeDeviceCover`: that function reads `readEmbeddedIdentity(sourceFile)`, i.e. an `open` on the device file, and D6's whole constraint is that the pass adds no opens — a cold device measures ~72 s of them. So the pass names each entry from the **cached** identity (EXTH 113/501, already read by the header pass) and shares everything after that: the fitted encode, the marker unlink limited to the exact name, the `mkdir`, the write. This is a reading, not a detail: the spec's D6 names the cost and never says which function writes. _Beat:_ the pass calling the shipped writer and paying 1,567 opens for entries whose identities are already in SQLite. _Revived:_ if the identity cache is ever absent on a path where the pass must run.
- **R4 — "already had an entry" is decided by one `readdir` of `system/thumbnails/`, by exact filename, with no stats.** The cache directory's own absence means nothing is there (the first pass on a device whose cache was empty). _Beat:_ `stat`ing each candidate entry, which is a device read per file for a fact one directory listing already carries. _Revived:_ if a truncated entry ever becomes possible — the write is a single `fs.writeFile`, so it is whole or absent.
- **R5 — the worker pool is over _books_, not entries.** Each book's jacket is read and encoded once, then written to every entry name that book's files need. _Beat:_ pooling over entries, which re-encodes (and re-reads off the share) the same jacket for a book sent in two formats. Bound: 8, the same bound `KEY_WORKERS` measured on this mount, because both passes are paying the share's per-file latency rather than its throughput.
- **R6 — a device file two library books both claim gets no entry.** `deviceFileOwners` returns both `(file, book)` pairs — presence already answers both — but the pass writes nothing for that file, because choosing between the two jackets is choosing which book wears the wrong one. This is D7's ambiguity guard applied one step further: the rule refuses a file that names _no_ book, and the pass also refuses one that names _two_. _Beat:_ last-writer-wins over the pairs map, which is a nondeterministic wrong jacket. _Revived:_ a census showing the case is common enough that the covers it costs are worth more than the risk — it is not common on this device (the guard's own arm requires a filename that matches one book and an inner title that matches another).
- **R7 — the pass's entire surface is one log line, emitted once per run that had owners to consider.** The parent spec's D5 said "a failure or a skip logs", and D6 said the count is what makes the first pass visible; for a pass that writes 700 entries unasked, one line with the breakdown is the honest form of both. Idempotence is asserted on the _report_, not on the line's absence. _Beat:_ staying silent unless it wrote something, which leaves the expensive first pass — the one D6 prices — with no evidence at all. _Revived:_ if it reads as noise on every connect; the fix is one condition.
- **R8 — the jackets are read only while the library is online, and the gate lives in the path resolution** (`nas.isOnline()` → the root → `join(root, book.nasPath, book.coverFullPath)`), which is the shape `library-edit.ts:36` already uses. A pass that runs unasked over 1,500 books is a different exposure from one send: the encoder is **synchronous** on the main process, so a jacket path under a share that has gone away is a stall, not a caught error. Offline therefore costs the entries and nothing else. _Beat:_ attempting every read and counting the failures. _Revived:_ a measurement showing `nativeImage.createFromPath` on an unreachable share fails fast on this machine.

Re-run: **12/12**. Generalised into `docs/invariants/device-transfer.md`'s testing section — _when a guard duplicates its caller's guard, the case has to come from the side where the caller's guard does not apply._

**Deviation from the plan, recorded.** AC11 and AC12 were planned into `device-covers.test.ts` and AC13 into `device-manager.test.ts`; the build put **the entries that actually land** (AC11/AC12) in `device-manager.test.ts` and **the pass's own logic** (AC14–AC17, AC17a) in `device-covers.test.ts`. **A case the design implied and the build had to rebuild.** The pre-build annex said the stand-in "must gain three calls before any case runs (`mkdir`/`writeFile`/`unlink`)". Tracked like the rest, which also makes the entry assertions impossible to race (the pump waits on tracked calls).

**Not decided here.** The two device readings (Risks 2 of the parent spec) — whether the Kindle renders a **fitted** (non-330×500) entry, and whether the marker spelling `…_portrait.jpg.tmp.partial` matches its firmware — are still open and still gate nothing, and the **first connect's cost** is still unmeasured (the pass reports it).

**The four readings to take, in order of what they change:**

1. **`ls /Volumes/Kindle/system/thumbnails/ | grep tmp`** — the marker suffix the device actually uses. If it is not `.tmp.partial`, `COVER_MARKER_SUFFIX` is one constant and the deciders are the two marker cases.
2. **Does a fitted entry render?** The pass writes 330×441 for a 1:1.336 jacket. Find such an entry after a connect and look at the home screen. If the device ignores a non-330×500 entry, the fix is _forcing_ the box (the stretch D3 rejects) and its decider is a new pure case on `deviceCoverSize`.
3. **The pass's own counters, from the app's log on the first connect** — that is the cost number Risks 5 left open, and the entry total worth recording against the 1,567 files.
4. **Whether the device litters a fresh marker** beside an entry the pass just wrote (Risks 3). If it does every connect, the cost is one `rm` per affected book and nothing else — measured, not assumed.

The harness this session needs already exists and starts in this state: `device-manager.test.ts` and `device-covers.test.ts` build their own fake volumes under a fresh temp root per case and touch no real volume; nothing has to be stood up.
