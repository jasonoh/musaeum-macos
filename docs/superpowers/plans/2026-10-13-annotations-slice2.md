## What this slice is

1. A **selection becomes a highlight**: the engine captures the selection's _index and CFI_ beside the text it already reports, a **chip** appears at the selection's own rect, and activating it writes the record slice 1 owns.
2. A **Notes panel** — the reader's one side slot's **fourth** occupant — lists the book's highlights in document order, groups them by section, shows a **stale** one with its quote and never hands it to the engine, and gives the active one an inline note editor and a Delete.
3. A **draw layer**: the engine's `draw-annotation` arm draws `Overlayer.highlight` in a new `annotation` palette role, re-offers the plan on every section render, and re-runs it when the resolved color moves — the obligation `ReaderSearch` already discharges, for the same measured reason.
4. One line outside the reader: **the delete dialog's copy names the notes** (AC19, D4).
5. **Nothing else.** No sidecar file, no migration, no `metadata.json`/`catalog.json` member, no wire change, no `vendor/` edit, and no new `musaeum://` host. The Python suite staying at **413** is the check on that boundary, not a hope.

## Readings this slice settles

Slice 1's annex alphabet used `R1`–`R8`; this series continues at **R9**, so a number quoted anywhere in this feature names one reading and one only.

**R9 — the lib refuses a gesture it cannot make a record of, and the refusal is `null`.** `annotationFromSelection` returns a complete locator or `null`; never a partially-filled object. _Alternative beaten:_ return what it has and let the caller decide, so the chip can still fire on a bare caret. It loses because the service refuses the same input one round trip later (`annotations.ts:342-345` — a blank `cfi` or a whitespace-only `quote` throws), so the choice is not "refuse or not" but "refuse at the gesture or after a NAS write attempt", and the second one has to say so on a toast. _Reversal:_ a caller that needs the _reason_ — then the return becomes a small discriminated result, never a partial.

**R10 — the locator's members are exactly the six a caller may say, and the context is computed by the engine and clipped by the lib.** The engine reads the text either side of the selection out of the section document with `Range.toString()` — the same model `sectionOffset` uses (`ReaderEngine.tsx:307-322`), so a stored `prefix` and the page it came from are measured the same way — and hands them to the lib, which reuses `clipQuote`/`clipContext`/`normalizeQuote` from `@shared/annotation.types` rather than re-deriving the caps (`QUOTE_MAX`, `CONTEXT_MAX`). _Alternative beaten:_ the engine clips them where it measures them. It loses because then two modules decide one rule, and the rule lives in the file's validator's own module. _Reversal:_ a caller that must supply an already-clipped context (an importer of someone else's annotations).

**R11 — `percent` and `sectionLabel` come from the reader's live session state, not from the selection's own arithmetic.** The chip records the page's own fraction (the store's `percent`, which is the number the progress bar is already showing) and the engine's `sectionLabel`. _Alternative beaten:_ derive the fraction from the section index over the spine length. It loses because a second derivation would disagree with the progress bar on screen, and the reader already has one percent the position store travels by (`reader.md:86`). _Reversal:_ slice 3's re-anchor, where the anchor is document-relative and page-relative stops being the same thing.

**R12 — the plan drives the engine and returns what it could not draw; the filter, not a catch, is what keeps a stale locator off the page.** `planAnnotations(annotations, color, source)` resolves to `{ rows, undrawable }`. Each row is `{ id, cfi, kind: 'highlight', color }`. A `stale` annotation is in **neither** list: it is not offered at all (D6's rule lives in the filter), and a `source` call that throws puts its id in `undrawable` and the plan continues. A value is offered at most once per plan. _Alternative beaten:_ let the engine's throw escape — which is what the engine's own re-add path does (`view.js:416` calls `addAnnotation` un-awaited and un-caught, and `:385` destructures `resolveNavigation`'s `undefined`). It loses on the failure the whole design exists for: one unresolvable locator must cost that annotation, never the book (R3 of the spec's _Risks_, AC14). _Reversal:_ an engine that _returns_ resolution failure instead of throwing — then a return value, not a catch, decides it.

**R13 — the plan is re-run, not amended; removal is the one derived exception.** It runs on every `relocate` — the seam the build moved it to — on the list changing, and on the resolved color moving. _(Amended 2026-10-13, when the build read the vendor's ordering: this reading first named `create-overlay`, the vendor's own re-add seam (`view.js:406-420`), and that seam is **too early to draw from** — the event is emitted before the paginator attaches the new overlayer, so a re-add inside it resolves against the previous section's overlayer and document, or against nothing at all on the first section. `relocate` is emitted after `this.#view = view`. The reasoning sits at the listener in `ReaderEngine.tsx` and in *Built* below; the decision above is unchanged.)_ Re-running is safe because the engine removes the value it is re-adding on the way in (`overlayer.remove(value)`, `view.js:389`), so a re-offer is idempotent. The one thing a re-run cannot do is _un_-draw: a deleted highlight's rect would stay on the page, so `removedValues(previous, next)` names the values to hand `deleteAnnotation`. _Alternative beaten:_ patch the layer incrementally (add/remove per change). It loses because the engine keeps no per-value state the app can read back, so "what is on the page" would have to be tracked twice. _Reversal:_ a measured cost on a long book — the plan resolves one CFI per annotation per section render, and its first symptom would be a late page turn above a few hundred annotations.

**R14 — the draw is selected by the row's `kind` through a table, not hardcoded in the listener.** The engine reads `kind` off the annotation object it handed the engine (the engine passes the whole object through in the event detail, `view.js:392-393`) and picks the draw function from a `highlight`-keyed table. _Alternative beaten:_ hardcode `Overlayer.highlight` at the listener. It loses on the criterion: AC16 says the plan _names_ the draw, and a name that nothing reads is a comment. The vendor's own reference layer reads the color off the annotation object the same way (`reader.js:178-182`). _Reversal:_ a second kind the plan emits — D2's reserved `bookmark`, which is a position and would want an outline.

**R15 — the chip's rect is the selection's client rect translated by the containing frame's own rect, and it is a `fixed` control in viewport coordinates.** `range.getBoundingClientRect()` inside the section document gives the rect in the frame's own viewport; `doc.defaultView.frameElement.getBoundingClientRect()` gives that frame's place in the top document (the paginator's iframes are same-origin — `align` `sandbox="allow-same-origin allow-scripts"`, `paginator.js:244`). Summing them puts the chip at the selection without reaching into foliate-view's closed shadow root. **If either rect is unavailable the chip is suppressed** rather than guessed at. _Alternative beaten:_ map through `screenX`/`window.screenX`, which breaks under display scaling and with the window's own origin; and a marker _inside_ the section document, which the paginator positions and the reader cannot style. _Reversal:_ `frameElement` answering `null` in the running app — then the geometry comes from the host's own rect, priced against the mis-position it costs, and the frame that shows it is AC20's.

**R16 — activating the chip creates and does not open the panel.** The chip hides on a successful create and the drawn highlight is the feedback; the person clicks it when they want to write a note, which is D8's second gesture. _Alternative beaten:_ open the Notes panel with the new annotation active. It loses because it moves a gesture the spec put at the highlight onto the chip, and the panel is a side slot that displaces the book's width — a cost worth paying when asked for. _Reversal:_ a person who cannot find the highlight they just made (a `stale`-from-birth record, or a subtractive theme), which is also when the panel should open on it.

**R17 — the panel's order and grouping are pure, and they are the lib's fourth responsibility.** `annotationGroups(annotations)` sorts by `percent`, then `created_at`, and groups by `section_label` with `groupLabel`'s own rule for an empty one (`reader-search.ts:154-156`) — the find panel's grouping, reused rather than re-decided. _Alternative beaten:_ sort in the component, where the renderer's missing DOM harness (`reader-search.ts:21-24`) would leave the rule undecided. _Reversal:_ a grouping that needs the engine's TOC progress rather than the stored label — then a stored label that is empty and a section the TOC names would have to be reconciled, which is a different feature.

**R18 — the fourth occupant is opened from two places and both funnel through one action.** `toggleNotes()` is the header control and `openNotes(cfi)` is D8's click-on-a-highlight; the second is the same open plus the active id, so there is one place that decides what "the panel is open" closes. _Alternative beaten:_ two independent actions that each close the other three. _Reversal:_ a third opener with a different reset rule (an export preview that must not clear the active row).

**R19 — the store owns the writes, and every write answers the list it adopted.** `loadAnnotations`, `addHighlight`, `saveAnnotationNote` and `deleteAnnotation` live in the store beside `beginReflow`, for the reason that one lives there — the answer decides more than one thing (the list, the read state, the active row) and one function that reads all of them is the only place that can be seen to agree with itself. Slice 1's R1 is discharged here: the write re-reads the file, so the answer's list is adopted whole rather than appended to. _Alternative beaten:_ the components call the bridge and patch their own copy. _Reversal:_ R1's own — a book whose list is large enough that a whole-list answer is felt on every note save.

**R20 — the three read states are three sentences, and none of them is a reader error.** `ok` renders the list, `missing` renders the empty state, `unreadable` renders the named refusal ("your notes are still on disk, they just could not be read") — and while a load is in flight the panel says so rather than showing the empty state. _Alternative beaten:_ fold `unreadable` into an empty list. It loses on slice 1's R3, which exists precisely so the panel cannot claim a person never wrote a note. _Reversal:_ none; this is the state R3 bought.

**R21 — the dialog's whole-book sentence names the notes and the partial-format sentence does not.** "This permanently removes the book, all its files, covers, notes, and metadata…" is the `wholeBook` branch only. Deleting one _format_ leaves the book, so it leaves the book's notes, and the branch's existing sentence already says the book stays. _Alternative beaten:_ name the notes in both branches. It loses because it would be false about the partial path — `deleteFormats` never touches a file that is not a book format (`files-and-deletion.md:17`). _Reversal:_ a per-format delete that takes the notes, which the record's per-book (never per-format) placement makes impossible without moving the store.
