## Known issues / risks

- **The tree carries formatting drift in 133 tracked files, and the drift includes trees this repo must not edit** (measured 2026-09-25, on `dc13218`, with `prettier@3.9.5`). 35 of the 133 are `vendor/foliate-js/**`, which invariant 11 forbids editing, and 24 more are the owner's own `.claude/` and `.obsidian/` — so `prettier --write .`, the documented-unsafe command, would silently violate an invariant and reformat two trees nobody in this repo owns. **The decision this waits on:** whether `.prettierignore` should name `vendor/`, `.obsidian/` and `.claude/` so a repo-wide check means "our files are formatted" (then one `format:` commit over the ~95 remaining files, ~23 of them code), or whether the gate stays per-file, which is what this repo has actually practised since 2026-07-12. Not a bug either way; do not fold it into a feature's commit.

- **`nas-manager.test.ts` is load-sensitive** (found 2026-09-25, not fixed): with a second Musaeum instance running and an `electron-vite build` in the same minute, _checkHealth › mounts nothing at all for a share nobody named (D5)_ (`electron/main/services/nas-manager.test.ts:208`) failed in two consecutive full-suite runs (`expected 'reconnecting' to be 'disconnected'`, then 2 failures), and passed in **four** consecutive runs afterwards — isolated (13/13, twice) and whole-suite (1605/1605, twice). The case asserts a state machine whose landing depends on real timers and on the health-check ladder, so the machine's load is in the assertion's critical path; the module's own suite is otherwise the decider for that ladder (see 2026-09-24 above). It is not this session's change (no main-process file is in that diff) and it is not a mystery to hand to the next session as a failing gate — treat a red there as `flake` first and re-run before investigating.
- **Goodreads scraper fragility**: `fetchers/goodreads.py` parses `__NEXT_DATA__` with an HTML fallback; markup drift silently disables series data (by design). Revisit if series coverage drops.
- **Edition mismatch on hydration**: embedded/Calibre identifiers now always win (fixed 2026-07-12), but fetched publisher/date can still describe a different edition than the file. Acceptable for now; watch during dry run.
- **Kindle path untested on hardware** — detection + transfer logic verified by code review only; test with a real Kindle over USB.
- **NAS behavior untested against real SMB** — offline mode was verified with a local folder; test mount-loss/reconnect against `//nas.smb`, especially mid-import and mid-transfer.
- **FTS tags matching**: `books_fts.tags` indexes the raw JSON string; quoted punctuation is tokenized away in practice, but verify tag search feels right with real data.
- **`deleteBook` FK restriction (pre-existing)**: deleting a book that has `device_history` rows throws (FK has no ON DELETE and `deleteBook` doesn't handle history). Found while building `replaceAllBooks` (2026-07-17).

- **`requirements.md` now overlaps `docs/architecture.md`** (2026-09-15). The 485-line original spec is still the better record of _why_ the pieces are shaped the way they are, but its architecture, schema and IPC sections duplicate the docs. Decide whether to fold it in so there is one architecture source, or annotate it as historical and leave it alone.
- **The `imports/` inbox watcher has never run and has no test** (found 2026-09-23, while scoping the phone's upload). `services/file-watcher.ts:15-32` watches `{library_root}/imports/`, imports anything with a watched extension through `importer.addFiles`, and then deletes the source — and the inbox holds **0 files** (mtime Jul 14), so it has never fired on this library. Nothing in the suite names it: there is no `file-watcher.test.ts` beside it. It is nonetheless _live_ — `index.ts:232-233` arms it on launch and on every NAS reconnect. One claim is verified and one is not, and one is a hazard. _Verified:_ a write through the mount **does** fire on chokidar **4.0.3** (measured 2026-09-23 in a scratch dir on the share: `addDir` +26 ms, `add` +4327 ms once `awaitWriteFinish`'s 2 s settled, `change` +8289 ms) — note chokidar 4's only dependency is `readdirp`, so this app's watcher is `fs.watch`, not the `fsevents` backend the top-level `fsevents@2.3.3` belongs to (tailwindcss's and vite's chokidar 3). _Unverified:_ whether it fires for a write made by a **different client**, which could not be measured because macOS refuses to mount the same share twice (`mount_smbfs: File exists` for the Bonjour name, the IP and a port-qualified spec). _Hazard:_ its success path is an `rm`, so a bug here silently destroys the file it took. Decide — test it or remove it. The phone's upload deliberately does **not** build on it: bytes land in the app's own scratch directory instead, one writer per landing zone.
